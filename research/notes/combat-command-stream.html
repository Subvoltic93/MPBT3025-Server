Native combat command stream (0x81)

Historical local paths in this document are relative to the original workspace root. Original client assets, client-derived research, and visual evidence remain in the separate workspace-root client/ directory and are not included in this server project.

Static and executable-fixture evidence from the supplied September 2001 BTCombat.dll; preferred image base 0x69000000. The server now encodes the command envelope and a controlled stock COM-4D setup. Two-client native combat entry, position relay and fire relay have been demonstrated. Standalone fire parsing and reference validation now have captured-packet/native-fixture tests; authoritative hit/damage and match completion remain unfinished.

ReceiveCombatData (0x6905cd60) forwards the PDU body and length to 0x690755c0. The bounded stream is processed by 0x69075060 before dispatch. The command type reader (0x69074b30) subtracts 0x21 from one wire byte and looks up the result in the factory registry at 0x690d4b50. Parsed commands are queued through 0x690753b0. Command application uses the visitor table at 0x6908e6a8.

The command-to-visitor trampolines are 0x6906f1a0, 0x69072540, and 0x69072e40 respectively. The callbacks provide independent semantic confirmation: NewMechCommand calls exported FillMech at 0x690411a0; TitleCommand calls FillReality at 0x69057a60, which ends by calling PrepareForCombat at 0x69056160. The ready callback calls exported ReadyForCombat at 0x690570e0, including GraphicsManager::EnterCombat. Thus the stream has explicit preparation and entry commands beyond the shell-level 0x80 message. The later executable fixtures and live preparation barrier trial below established the required initialization sequence.

Encoding details recovered so far

  • Small values and command types use one character with bias 0x21.
  • Multi-character integers use base85, also biased by 0x21. Reader 0x6906a180 multiplies by 0x55 for each following digit; its width argument 1..4 selects 2..5 encoded characters. Do not serialize these as raw u32.
  • The two-/three-width signed helpers (0x69074c90/0x69074cc0) subtract fixed biases after decoding. Other helpers decode bounded unsigned values.
  • Preprocessing removes outer framing (0x690751c0), checks/removes a three-character checksum (0x69075110), then removes an inner prefix (0x690750b0). The matching serializer inserts 0x21 as the inner prefix and ESC framing around the checksummed stream. Executable native fixtures now confirm both checksum directions and terminal NUL semantics (below).
  • TitleCommand decoder is 0x69072c90. It reads a string, two bytes, four bounded integers, then several one-character values. These member offsets are relative to its serialization subobject; account for the subobject offset before matching FillReality accesses.

The ready factory decoder at 0x69072470 constructs through 0x690722d0, which invokes the no-op decoder 0x6906b7f0. Its payload therefore appears empty after the type byte; the native writer fixture confirms exactly _.

Native fixtures now cover Title, NewMech, Ready, and stock COM-4D equipment. A controlled setup trial is behind -experimental-combat-init; it is disabled by default. It supports peer position/fire relay, with no authoritative hit/damage simulation.

Stream checksum and title layout follow-up

The checksum routine at 0x69075200 is the same 19-bit LFSR described in ../../../../MPBT3025/references/solaris-protocol-reference/solaris_server.py (which documents the related Solaris COMBAT stream). Its seed selection is directly visible in the BTCombat DLL: when the stream context flag at this+4 is clear, the seed is 0xC4545 (804165); when set, the 32-bit addition wraps to 0xA5C45 (678981). The reference identifies 678981 as the server-to-client COMBAT checksum seed. Each checksum is encoded as three base-85 digits after the inner-prefix byte and command payload. The title command decoder reads a length-prefixed string, two one-byte fields, four two-byte-width base-85 integers, one one-byte field, three more one-byte fields, and a final one-byte field. Its serialization subobject fields sit at offsets 0x2c and 0x3c..0x54. FillReality consumes these as map/reality setup values, and then calls PrepareForCombat.

This is enough to construct a byte-level envelope, but the semantic values for the TitleCommand and the complete NewMechCommand remain unverified. Do not send a guessed 0x81 stream yet: a checksum-valid packet can still install an invalid terrain or mech state and crash the native client. Next match the TitleCommand fields against the known Solaris CombatInfo and recover the NewMechCommand decoder/model fields before the first controlled stream trial.

Executable native fixtures and first setup trial

scripts/native-combat-fixture.py maps the supplied DLL's PE sections into an isolated Linux i386 executable at their original addresses. It calls the original command writers (Title0x69072be0, NewMech0x6906e830, Ready0x6906c600), prefix/checksum/framing routines, and receive preprocessing. It substitutes only a bounded raw-buffer write method and memmove; it does not initialize a DLL, connect to a server, attach a debugger, or modify a client. The DLL SHA256 is pinned to prevent applying offsets to another build. Generated JSON fixtures in data/test-fixtures/combat-native-* record original bytes and both direction checksum results. Native preprocessing must recover the exact original command before a fixture is accepted.

October 23: fire references and standalone batches

Absolute armor assignments and collision parts

The native damage command's second AddDamage argument is an absolute remaining value, not an incoming damage delta. Resolver0x690500c0 subtracts incoming weapon damage from Mech armor at+0x190, queues slot21+armor with the remainder, and transfers excess to internal structure at+0x1e8 (slot32+internal). Original Damage0x690484c5..0x690484e1 only replaces an armor value if the new value is smaller. Applying a delta directly would corrupt state.

scripts/native-damage-fixture.py executes that resolver and original GetDamageState0x69047fd0 with synthetic current/max armor arrays and internal structure. AddDamage is replaced with a bounded triple recorder. It separately executes original Damage with an inert Reality getter and non-local Mech to avoid rendering/server callbacks. These substitutions are explicit in the fixture; no native server initialization, clients or networking run.

This fixture does not cover destruction, critical hits, depletion of internal structure, transfer chains, missile impacts or piloting-target calculation. The third argument propagates unchanged into damage event callbacks as a credit entity. Its server use still needs authenticated attribution. CombatDamageCommand encodes the explicit-entity c command and rejects field overflow. It is deliberately not yet emitted by the relay.

SendShotCommand0x69049f95..0x69049fd1 copies HitReturn's entity+1 and part+1 to client fire object+0x31/+0x34. The latter serializes as three unsigned base85 digits at command bytes3..5. Direct/local resolution0x6904a0dc passes those HitReturn values to GetMech and the armor resolver. Therefore the wire entity is a collision report, rather than merely the selected HUD target. Terrain collisions use another part space when no Mech entity is reported. Both saved opposite-direction laser batches decode to Mech armor part4. The relay now rejects Mech reports with missing/out-of-range parts (valid0..10), while preserving the separate terrain/untargeted space. This validates references; it does not independently validate collision geometry or award damage.

Position and range follow-up

Native client position command 0x27 begins with signed four-digit X and Y. The decoder subtracts 85^4/2, the inverse of the setup encoder. Captured live position reports decode to (0,10000) and (0,-10000), matching the mirrored diagnostic launch coordinates; FillMech scales those coordinates by 0.01, producing the verified 200m pair spacing. The relay now retains the latest reported X/Y and the following 15 opaque pose-field bytes per authenticated entity in the active mission for diagnostic correlation. These fields remain client supplied and are not used to authorize damage.

CWeapon::Init copies six medium-laser range values to weapon object +0x34..+0x48: [45,90,135,180,225,270]. The use of those values as accuracy bands or as a hard firing range has not yet been confirmed, so they do not yet support a server range gate. The fire visitor consumes additional reported coordinates at object +0x4c, +0x50, and +0x54. SendShotCommand 0x69049e60 copies HitReturn's three doubles from offsets +0x10, +0x18, and +0x20, multiplying each by100 before storing them. The fire writer serializes these as signed four-digit values at client command bytes23..34. Both saved live shots decode to (-9936,13891,0) and (9930,13891,0) in hundredths of a world unit. ParseClientCombatFire now exposes that reported point, and a regression decodes both original captured frames. This confirms the point's source and scale; it is still client supplied. Compare it against authenticated-room positions and recover the coordinate axes and native hit tolerance before using it to authorize damage.

ParseClientCombatPositionCommand decodes the first two signed coordinates of the same native 0x27 command. The regression reads both from the original saved 0x81 frames as (0,10000) and (0,-10000). Neither that decoder nor the fire-point parser changes relay behavior or promotes either report to authoritative state.

The server 0x41 peer-position command follows the native receive path below. It applies client-reported pose fields through Mech::SetPosition in combat state3. The server retains only reported X/Y for correlation; complete pose field semantics, world-axis transforms, and Mech collision volume/tolerance remain unknown.

Peer-position receive visitor mapping

The server key 0x41 registration thunk 0x6906f450 registers its factory through 0x69073e40. Factory 0x6906f1c0 allocates a 0x50-byte wrapper, sets an outer vtable at the object base, and an embedded command subobject vtable at base + 4. It passes that embedded pointer in ECX to decoder 0x6906f3d0. Consequently, decoder fields at +0x2c (entity), +0x30 (X), +0x34 (Y), +0x38 (heading), and +0x3c..+0x48 (remaining pose fields) appear at wrapper offsets +0x30, +0x34, +0x38, +0x3c, and +0x40..+0x4c.

This matches visitor callback 0x69073640: it reads the entity byte at +0x30, pose data beginning at +0x34, requires combat state3, scales the pose values, and calls Mech::SetPosition 0x69045920. The callback is also visitor-table slot1 (0x6908e6ac). This establishes the native peer-position receive/application path and corrects the earlier overly cautious checkpoint. The server relay now stores the last reported X/Y and 15 opaque pose-field bytes by authenticated entity for each active mission. It clears this cache on launch, mission departure, and disconnect. Axis meaning, transformed world coordinates, collision volume/tolerance, and whether a client-reported HitReturn point corresponds to a server-validated hit remain open; do not use the collision report alone to authorize damage.
