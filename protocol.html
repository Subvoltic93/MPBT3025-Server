Protocol and Server Operation

This document describes the current Go server implementation. It covers both network addresses and message addresses (PDU IDs). A numeric ID listed below is handled only in the direction and context stated.

Listener addresses

The server speaks TCP with Aries framing. It does not serve HTTP.

Address Use
127.0.0.1:15000 Default local bootstrap listener (-listen). It accepts the client’s primary connection and handles lobby, planet, room, and combat traffic.
127.0.0.1:15001 Optional secondary Aries listener (-world-listen). It is started only with -planet-redirect; a successful planet join can be redirected there as an experiment.
127.0.0.1:15011 Development trial address used for the current isolated test instance. It is selected explicitly with -listen 127.0.0.1:15011; it is not a second default service.

All default listeners bind to loopback, so they accept connections from this machine. Use -listen or -world-listen to change a bind address. Binding to a non-loopback interface makes the service reachable on that interface.

Direct client launch argument

The direct launch passes aol:<server-host>:<server-port>:key:<local-key> to BT3025.exe (or to the Linux/Wine helper that launches it). For the default listener, the argument is aol:127.0.0.1:15000:key:local-dev. aol: is the legacy startup argument that selects the Aries TCP endpoint; the host and port must match the server's -listen address. On Windows, launch the existing BT3025.exe with this argument from its installation directory. For a LAN server, bind with -listen 0.0.0.0:15000 and put the server machine's reachable LAN address in the client argument.

This direct path bypasses the retired EA/GILS sign-in and launch service. The local key is only a development connection value; it is not an EA credential, and the emulator does not validate EA accounts or tickets. The client launcher and game files remain in a separate local client workspace and are not part of this server repository.

The persistent campaign file defaults to runtime/world.json (-world). Text packet traces default to runtime/traces/ (-trace-dir); each connection creates a session-<timestamp>.log file. The current isolated trial uses runtime/world-test-15011-armor-probe.json and runtime/traces/armor-probe/.

Aries transport

Each TCP frame begins with 12 bytes:

Offset Size Meaning
0 4 Message type, little-endian
4 4 Tag, little-endian
8 4 Payload length, little-endian
12 length Payload, at most 1 MiB

The server sends transport type 0x16 (LOGIN_REQUEST) after accepting a connection. A client 0x15 (LOGIN) receives the game host greeting inside a data frame. Type 0x00 is a data frame; type 0x03 is a redirect frame. Other transport types are logged as unimplemented.

Game PDU framing

A game PDU is carried in an Aries data-frame payload. Its six-byte header is big-endian: a 16-bit message ID followed by a 32-bit total PDU length, including the header. Multiple PDUs may be decoded from one data payload. The client buffer limit used by the server is 0x4000 bytes.

For oversized messages the server emits SPLIT_BUFFER_PDU (0x47) wrappers containing a final-fragment byte, a 32-bit byte count, and a chunk of the original encoded PDU. The serializer shape is recovered; complete client-side reassembly behavior is still uncertain.

Current connection flow

  1. A TCP connection receives LOGIN_REQUEST; a client LOGIN receives HOST_ONLINE (0x1D).
  2. CLIENT_ONLINE (0x09) receives the local player record (0x3C), profile (0x3D), and an unsynchronized static-configuration update (0x86). The client’s STATIC_CONFIG_RESPONSE (0xA4) completes the sync exchange.
  3. Startup settings requests are answered with their default response forms. A CREATE_CHARACTER (0x87) request creates or loads the local pilot and receives the current zero-result completion form (0x88). The authentic success semantics of that response remain unconfirmed.
  4. A JOIN_PLANET (0x91) request changes the pilot’s planet location. Live connected occupants are announced with OCCUPANT_UPDATE (0x94) and arrival/departure messages (0x2B/0x2C). The server answers a rejected join with JOIN_PLANET_FAILED (0x92).
  5. LIST_ROOMS (0x26) receives an empty LIST_ROOMS_RESPONSE (0x27). Solaris staging rooms are maintained from world state and, when enabled, announced individually with 0x99, updated with 0x98, and removed with 0x9A. Populated 0x97 lists are not used in the tested path. A mission join uses JOIN_ROOM (0x23); leaving can use EXIT_ROOM (0x17) or the client’s parent-city rejoin path.
  6. READY_STATE_CHANGE (0x8C) requests update the selected Mech or readiness state. When the room is ready, the scheduler publishes a countdown and the clients enter combat together.
  7. COMBAT_DATA (0x81) streams accept a leading position, standalone fire, and multiple complete fire commands. Unknown or truncated tails reject the batch. Only a valid position can satisfy the preparation barrier. Once combat is active, supported commands relay to peers in the same launched room. For diagnostics, the server retains each active member's latest reported X/Y and 15 opaque native pose-field bytes under its authenticated combat entity; the cache clears on launch, mission departure, and disconnect. These fields are client supplied and are not used for hit or damage decisions. The server authenticates the shooter, restricts weapon slots to the stock COM-4D loadout (0–2), and requires a reported target to belong to that room. Untargeted shots remain valid. These are reference checks; aim, range, line of sight, ammunition, hits, damage, destruction, and match results are not authoritative.

Unknown game PDUs are ignored except for the recognized startup-setting request IDs, which receive default-form responses. This is a deliberately small local emulator, not a complete recreation of the legacy online service.

Room counts and sides

Live occupants are tracked by connected sessions, not by the saved pilot list. Solaris staging RoomIDs are city-specific: roster snapshots, counts, arrivals, and departures are limited to the same planet and city. Seated pilots remain visible to staging viewers in their own city; mission rosters are limited to their mission. Mission occupancy and open seats come from the room’s actual seats, including AI seats. The Solaris room encoder places defender-seat values in the Alpha-facing field and attacker-seat values in the Beta-facing field, based on the current row-renderer observation.

The October 23 native trial verified Alpha 1/4 and Beta 0/4 for one Alpha pilot, reset to 0/4 after Back, both pilots in the settled staging roster, and both COM-4D seats under the correct mission headings. Ready and cancel changed both visible statuses and the countdown. A separate regression verifies that another city cannot affect the staging roster or count. Native cross-city navigation, reconnect, and same-side assignment remain to be checked; see the session evidence.

Native fire references

The 36-byte client command begins with +, followed by one base85 digit for weapon slot and one for collision entity plus one, then three unsigned base85 digits for collision part plus one. Zero means absent; otherwise subtract one. SendShotCommand copies these from HitReturn, rather than the selected HUD target. It also copies the reported hit point to signed four-digit values at bytes 23–34 after multiplying each coordinate by 100. These are client-reported coordinates, not an independently verified hit. The server e command inserts the authenticated shooter before those fields and omits the client's last byte. A Mech collision report must name a rostered entity and armor part 0–10; terrain/untargeted parts use another index space. Native serializer fixtures and captured shots cover these layouts; see combat research.

Experimental spawn arrangement

Native FillMech scales setup coordinates by 0.01 and computes facing toward the map origin (0x6904207e–0x690420fd). The experimental launcher now mirrors opposing lances across that origin: first seats are 200 metres apart, with 30 metre seat spacing. This controlled diagnostic arrangement replaces the almost parallel, 20 metre separation used previously. The October 23 follow-up confirmed mutual sight, 200 metre target selection, targeted laser reports in both directions and the incoming laser effect. The later opt-in armor diagnostic verified one synchronized non-lethal armor change per target. These remain diagnostic spawns, not recovered production spawn rules.

Native absolute damage assignments

Key 0x42 / wire c carries five one-digit values: entity, state slot, remaining value, credit entity, piloting target. CombatDamageCommand matches the native writer and rejects field overflow; the normal relay emits no assignments, while the opt-in diagnostic below emits one per target. Slots 21–31 represent absolute remaining armor, 32–39 internal structure. In isolated native runs, armor 15 taking 5 damage queues slot 25 = 10 for region 4; armor 3 overflows to slot 36 = 18 from internal 20. Original Damage only lowers armor: repeated 10 and older 12 assignments both leave it at 10. Server hit rules, component/destruction handling and piloting-target calculation remain unfinished.

Opt-in live armor diagnostic

-experimental-combat-armor-probe requires native setup. After valid active-room references, a slot-0 medium-laser Mech report can consume the target’s single diagnostic allowance. The server uses stock armor minus 5 and initial piloting target 4; depleted armor, internal damage and subsequent hits are outside this diagnostic. It sends c then e in one 0x81 stream to both authenticated room clients, including the shooter. The shooter’s visitor skips its own effect but applies the queued target assignment. Launch/departure/disconnect clears the allowance. Two native directions and a later ordinary shot are preserved in data/test-fixtures/combat-live-armor-probe.json. Geometry is still client-reported; this flag does not enable authoritative combat.

Experimental cumulative medium-laser damage

-experimental-combat-damage requires native combat init and excludes the one-shot armor-probe flag. In active initialized missions, server-owned COM-4D armor/internals process slot0 medium-laser reports with damage5, recharge5s and maximum range270m. Misses consume recharge. Damage assignments (c) queue before the matching fire (e) in one stream echoed to the shooter and peers. Native resolver differential fixtures cover all11 armor regions and internal transfer/weapon-disable records. Core/head internal depletion marks the server Mech destroyed.

The peer-position visitor establishes world coordinates (wireY, unsignedHeight, wireX) in hundredths. Reports must be at most2s old and the claimed collision point must fall inside an explicit trial envelope (10m horizontal radius, height-1..20m relative to target pose). This is coarse plausibility validation; collision-part reports and movement remain client supplied. Independent ray/mesh collision, occlusion, heat, critical hits, piloting-target evolution, ammunition weapons and match completion are open. Live cumulative damage delivery is pending at this checkpoint.
